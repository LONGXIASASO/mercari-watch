# 煤炉小卡监控 · 云端版

在 GitHub 的服务器上每小时抓一次煤炉（jp.mercari.com），把新上架的小卡推进云端页面。
**跑在 GitHub 的机器上，你自己的电脑关不关机都不影响。**

- 监控页：https://mercari-card-watch.app.workbuddy.host/?sharecode=L2A6N4ATZQ
- 监控对象：`AND2BLE ジャンハオ` / `ZB1 ジャンハオ` / `ジャンハオ`（宽词兜底）
- 节奏：北京时间 9:00 ~ 次日 1:00 每小时一次；**2:00-8:00 不跑**，9:00 那轮自动把前面 8 小时补上
- 页面保留：**近 2 天有更新**的（含老商品最近改过价/描述的），且每轮复查在售状态，已售出的缩略图上打标

## 一次性配置（约 10 分钟）

### 第 1 步：注册 GitHub

没账号就去 https://github.com/signup 注册一个，邮箱验证一下就行。

### 第 2 步：建仓库

打开 https://github.com/new

| 字段 | 填什么 |
|---|---|
| Repository name | `mercari-watch` |
| 可见性 | **Public**（公有） |
| 其他 | 都不用勾 |

> **为什么必须 Public**：商品图是靠 jsDelivr 从仓库分发的，jsDelivr 只能读公开仓库。
> 如果设成 Private 也能正常抓取，只是手机上又会变成「图片需梯子」。
> 仓库里没有你的任何隐私信息（分享码本来就写在前端页面里）。

### 第 3 步：生成一个令牌（当密码用）

GitHub 早已不允许用登录密码推送代码，必须用「令牌」。

1. 打开 https://github.com/settings/tokens/new
2. **Note** 随便写，比如 `mercari`
3. **Expiration** 选 `90 days`（这令牌只在这次上传用一次，过期不影响后面自动运行）
4. 下面的权限列表里，**只勾 `repo` 和 `workflow` 两项**（`workflow` 必须勾，否则推 `watch.yml` 会被拒）
5. 拉到最下面点 **Generate token**
6. 复制那串 `ghp_` 开头的字符（**只显示这一次**，先粘到记事本里）

### 第 4 步：上传文件

双击这个目录里的 **`上传到GitHub.bat`**，按提示输入：

1. GitHub 用户名（不带 `@`）
2. 粘贴刚才那串令牌（**粘贴时屏幕不显示字符，是正常的**）

推完窗口里会显示「推送成功」。脚本推送完成后会自动把令牌从本地配置里抹掉，不会留在这台电脑上。

### 第 5 步：手动跑一次验证

打开 `https://github.com/你的用户名/mercari-watch/actions`

- 左侧点「煤炉小卡监控」
- 右侧按钮 **Run workflow** → 绿色按钮
- 等 1-2 分钟，点进去看日志，最后出现 `完成：窗内 N 条` 就是通了

第一次跑会把近 24 小时的商品全收一遍，之后每小时增量。

### 第 6 步：关掉本机的旧定时任务（可选）

云端接手后，公司电脑那套就不需要了，避免重复跑。
到「任务计划程序」里删掉 `MercariWatch`，或者双击 `mercari_watch\卸载定时任务.bat`。

## 平时怎么用

什么都不用做。每小时自动跑，页面上直接看。

想临时补抓一段：Actions 页面 → Run workflow → 在 `hours` 里填 `48` 就是往回抓 48 小时。

### 页面上保留什么

- 默认显示**近 2 天有更新**的商品（`retain_days` 可改）—— 老商品只要最近改过价或描述，也算「有更新」
- 排序、筛选、时间窗全部按**更新时间**（`updated_ts`）算，跟煤炉「最新順」口径一致
- 卡片右下角是「多久之前更新的」；如果商品是更早上架的，会多一个橙色 `上架 MM-DD` 标签，
  一眼能分出「刚上架的新货」和「老货刚改过价」
- 筛选栏另有一组：`全部 / 仅在售 / 仅看售出`
- 每小时抓取时顺带复查这批商品的在售状态：
  **连续 2 轮搜索都找不到的，判定已售出**，缩略图上盖一个「已售出」标签。
  标签只盖缩略图，点开的大图照常显示原图。
- 为什么是连续 2 轮：万一某轮翻页没翻到底，单轮缺失会把还在的商品误标成售出。
  两轮确认能滤掉这种抖动。本轮只要有一个搜索词抓失败，整轮跳过售出判定。

## 改监控词 / 过滤规则

编辑 `config.json` 然后提交，下一轮生效。常用字段：

| 字段 | 作用 |
|---|---|
| `queries` | 搜索词，`on: false` 可关掉某个 |
| `queries[].all_time` | **`true` 表示这个词不限上架时间**，老商品也收进来（一般不用开） |
| `must_any` | 标题必须命中其中至少一个 |
| `must_not` | 标题命中就丢弃（排 SEVENTEEN 那几位） |
| `report_hours` | 每轮往回看几小时（按更新时间算，间隔更久会自动放大） |
| `scrolls_all` | `all_time` 的词要滚几次（滚到底才能捞到老货） |
| `imgs_max_per_run` | 单轮最多下几张图 |
| `img_keep_days` | 商品图留几天（默认 7 天，超期自动删，控制仓库体积） |

### 时间窗为什么不按「上架时间」算

煤炉搜索接口里每条商品除了 `created`（上架）还有 `updated`（最后修改），
而它的「最新順」实际是按 `updated` 排的。所以：

- 卖家**改价、改描述**的老商品会被顶到搜索结果前面 —— 这正是我们要抓的「有变化」的商品
- 脚本用 `updated` 判断是否在时间窗内、页面也按 `updated` 排序，两边口径一致
- 曾经踩过的坑：只看 `created` 的话，一条 10-11 上架、今天改过价的商品会被判成「太旧」直接丢掉

## 会不会超免费额度

- 每轮约 1.5-2 分钟，一天 17 轮 ≈ 30 分钟
- 一个月约 900 分钟
- **Public 仓库的 Actions 不限时长**（Private 是 2000 分钟/月，也够但不宽裕）

所以只要仓库是 Public，就不用管额度。

## 几点说明

**仓库体积**：每轮会提交商品图，脚本会自动删掉 48 小时前的旧图。
每次提交都用 `--amend` 覆盖同一个快照，所以仓库历史不会越滚越大，稳定在几 MB。

**为什么不用代购站的接口**：ZenMarket 的结果页是 JS 渲染、Buyee 直连 403、
煤炉官方 API 要 DPoP 签名。现在走的是「用无头浏览器打开煤炉搜索页、
截获它自己发出的搜索响应」，字段最全，还自带 `created` 上架时间戳。

**搜索词的坑**：`AND2BLE ジャンハオ` 这个组合在煤炉上几乎搜不到东西，
真正有货的是宽词 `ジャンハオ`。而 `ジャンハオ`（章昊）又会撞上 SEVENTEEN 的
`ジョンハン`（净汉）、`ジョシュア`，所以配了 `must_not` 去噪。

## 出了问题看哪里

| 现象 | 原因 | 怎么办 |
|---|---|---|
| Actions 里 job 标红 | 没抓到数据，或页面结构变了 | 点进去看日志里 `[watch]` 开头的行 |
| `上传到GitHub.bat` 报推送失败 | 仓库没建、名字不对、令牌没勾 `repo`+`workflow` | 见脚本失败提示里的 4 条，改好后重跑，重复推不会出问题 |
| 页面有商品但图是占位块 | 仓库是 Private，或图片还没提交 | 确认仓库是 Public；等 1-2 分钟 jsDelivr 生效 |
| 页面上没有任何数据 | 推送失败（分享码变了） | 检查 `config.json` 里 `cloud.push_url` 的 sharecode |
| Actions 两周没跑 | 仓库 60 天无提交会被自动停用 | 点进 Actions 页面有个 Enable 按钮，点一下恢复 |
